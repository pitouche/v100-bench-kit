## 3. Ce qu'on a creusé et ce qu'on a trouvé (par chantier)

### A. Bench préfill/gén vs contexte (1–2 oct) — `bench/`
- **Le débit de préfill est gouverné par la position absolue dans le KV (n_past), pas la taille du chunk.** Même diff de 32,5k : 547 t/s à 65k → 276 t/s à 195k (×2). Le token marginal d'un contexte chaud coûte +44 %/tok vs préfill froid de la même zone.
- Génération : pente linéaire **~3,4 ms/step par 10k de contexte** (69 → 132 ms/step de 2k à 192k) = la lecture-KV du verify domine.
- Artefact identifié : l'API rapporte les t/s de prefill **sur la diff** quand le runner restaure un checkpoint LCP (les « 1,5k t/s » initiaux étaient fictifs). Le runner réutilise par checkpoints KV + LCP : seule la diff est préfillée.
- Vision : tokens image ≈ (W×H)/1024+32 ; prefill vision ≈ 1/3 du texte.
- Ollama ≈ direct (cold +2 à +5 %).

### B. Autopsie Q8_0 (5–7 oct) — `autopsy-20261005/q8-qpn/ETAT.md` (la pièce maîtresse)
Chaîne P0→P7a, avec prod jamais touchée (fenêtres autoclose + trap de restauration) :
- **P0/P1/P2 — Tensor Core / QPN (port NInfer)** : NO-GO pour le decode T=4. Le port exact (prepack byte-exact, 25/25 correctness) est 2,7× plus lent que NInfer **à cause du régime PCIe/L2** (7 760 CTAs, 6 Mo de L2 → relecture poids 1,45×), pas du portage. Bascule TC > dp4a seulement à **T≥16** (préfill/batch).
- **P3 — ce qui plafonne le decode T=4** : le **débit DRAM des poids, atteint à 84 %** (757/900 GB/s sur lm_head). ALU/dp4a/déquant : ~0. Pas d'amortissement de tiling en prod (446 µs/token constant de T=4 à T=16, les poids sont relus T fois).
- **P4/P5 — ncols=8 existe déjà et paie** : `mul_mat_vec_q<Q8_0,ncols=8>` = ×1,49–1,63 en µs/token… **mais P6 : la prod n'y arrive JAMAIS** (MTP 3+1 avec -np 1 → ne1∈{1,4} exclusivement, zéro occurrence ne1=8 structurellement).
- **P6.5 — cartographie du cycle** : Q6_K = **57,3 %** du trafic poids (12,43 GB/cycle sur 21,68 GB), Q8_0 27 %, Q5_K 15 %. Attention KV ≈ 6–7 ms/cycle (second ordre). **~50 % du cycle (30–43 ms) non attribué** → c'est LA question ouverte.
- **P7a — le gate** (seuil fixé AVANT la mesure) : Q6_K 17408×5120 @ ne1=4 = **494,7 GB/s** vs ancre Q8_0 691,9 → **H1 confirmée** (les K-quants tournent sous-régime). Gain projeté 7,4–11,3 ms/cycle.
- En chemin : crash segfault libcuda root-causé = **bug du harness** (sous-allocation buffer poids, `ggml_row_size` appelé sur 1 bloc au lieu de la ligne) ; corrigé, traces conservées.

### C. Kernel Q6_K (8 oct) — `p7/` — **CLÔTURÉ 8 oct 18:50, non intégré**
- **P7 (X4)** : décodage du fragment Q6_K une fois / 4 colonnes (miroir du Q5_X4) → **+1,5 % kernel, +1,10 % applicatif** (60,71 → 61,39 t/s, reproductible, acceptance bit-identique, 0 régression) = ~0,4 ms/cycle, **sous le seuil de 2 ms** → **non intégré** (décision utilisateur : clôture propre).
- **P7b (hoisting scales)** : 0 (ptxas gardait déjà les scales en regs, 96 regs avant/après).
- `summary()` de `p7_ab.sh` corrigé (bug = format `:.4f` appliqué à la string `"NA"` via l'expression ternaire) + comparaison régénérée depuis les TSV sans re-run (`regen_compare.sh`).
- Diagnostic final du déficit 495 vs 692 GB/s : **structurel** — VDR_Q6_K=1 (2× itérations K-loop), dp4a émulé en sm_70, 96 regs → **latence/ILP-bound, pas bande-passante-bound**. Marge « patch local » épuise ; fermer le gap demanderait une réécriture complète (VDR=2 / TC) — hors budget.
- Prod : known-good `e4afbb4a`, revert clean, service actif. **Piste suivante actée : H2.**

## 4. Pistes FERMÉES (ne pas rouvrir sans nouveau signal)

1. **QPN / Tensor Core pour le decode T=4** (P0/P1/P2) — dp4a imbattable à T≤9 ; régime PCIe/L2.
2. **Kernel Q6_K par patch local** (P7/P7b, clôturé 8 oct) — marge exploitable ~+1,1 % ; le reste est structurel (VDR=1, dp4a émulé, 96 regs). Réouverture seulement via réécriture VDR=2/TC si H2 déçoit.
3. **Q5_K standalone** — gain max absolu 1,83 ms/cycle < seuil 2 ms.
4. **W4R4 fusé (FFN)** — refuté : le FFN n'est jamais fusionné au decode.
5. **GDN** — déjà 1 kernel fusionné, rien à faire.
6. **Exploiter ncols=8 (B8)** en prod — structurellement inatteignable (ne1≤4 avec MTP 3+1, -np 1).
7. **Profilage nsys T=4 pour le split W4R4/FA/GDN** — rendu caduc par P7a (le split poids est maintenant mesuré) ; la fenêtre nsys reste l'outil pertinent pour H2 (gaps).

## 5. Explorations qui peuvent encore jouer (classées par potentiel estimé)

### 🎯 H2 — Orchestration / gaps CPU (LA suite directe, c'est là que le travail s'est arrêté)
~30–43 ms/cycle (~50 % du cycle 76 ms) non attribués après P7a. Le poids n'est pas au plafond (495 vs ~750) mais le gain kernel maximal reste ~7–11 ms ; **le reste est ailleurs** : gaps CPU↔GPU entre les ~4400 nodes du graph, orchestration MTP (3 décodeurs/cycle), requant, samplers, sync.
- Outils déjà en place : `p5_ktrace.so` (attention : invisible en replay CUDA graph), `p7a_dispatch` comme harnais, journal `print_timing`.
- Méthode probable : events CUDA par étape du flux (pas interpose) ou ktrace en rejouant le vrai graph en fenêtre.
- Si H2 confirme des gaps CPU : c'est du scheduler/serveur, pas des kernels → gain potentiel bien plus gros que tout ce que le kernel Q6_K pouvait donner.

### 🔭 Q8 FA tensor cores étendu à T∈{1,2,3} (piste identifiée nuit 4 oct, jamais faite)
Le kernel Q8 FA TC n'est dispo qu'à **T=4 exact** (verify complet). Drafts MTP (T=1) et verifies partiels après rejet (T=1/2/3) passent en mma_f16 avec conversion Q8→f16 dans le tile — à 100k+ KV c'est du trafic + conversion inutiles. Option la plus sûre : **pad Q à 4 tokens avec mask** (0 nouveau kernel). Seuls ~28 % des rounds sont T=4 (acc pos0 ≈ 0,72) → c'est potentiellement une part significative du temps attention.

### 📈 A/B applicatif **long contexte** (~150–196k)
Le bench synthétique montrait que les gains kernels V100 **croissent avec le contexte** (+3 % court → +9 % long) ; l'A/B P7 n'a testé que du < 1k tok (+1,1 %). Le vrai cas d'usage (OpenWebUI 200k) n'a jamais été tranché en applicatif. Utile aussi pour mesurer l'impact du shortlist/defer en conditions réelles longues.

### ⚖️ Secondes cibles (moins prioritaires)
- **Préfill long-contexte** : la dégradation positionnelle (×2 de 65k→195k) n'est pas décomposée (KV longue traversée vs W4R4 vs FA). Si le cas d'usage est les gros prompts, un P2 « 32×8 fused TC » (déjà écrit et validé dans l'autopsie !) est le bon kernel au-delà de T≈16.
- **Turing SM75 / RTX 2080 Ti** : chemins inclus mais **jamais benchmarkés proprement** (handoff sept). Sweep `GGML_CUDA_TURING_CUBLAS_MIN_BATCH`, ncols2=2 long-K.
- **Batching multi-requêtes** : si un jour la prod sert plusieurs décodes simultanés, le B8 (ne1=8) devient exploitable (×1,5–1,6 sur les poids Q8_0) et le TC gagne dès T≥16.
- **Réécriture kernel Q6_K VDR=2 / occupancy** : le seul moyen de fermer le gap 495→700+ GB/s (~7 ms/cycle) — effort d'une réécriture complète, à faire seulement si H2 déçoit.
